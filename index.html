How It Works

TheBullpenBet runs machine-learning models against every MLB game and publishes the output here. This page explains what's happening under the hood — the inputs, the math, and what to trust.

The daily pipeline

Everything you see is produced by a single Python entry point, daily_update.py, that runs automatically several times a day. Each tick executes the steps below independently; one failing doesn't block the others, and every artifact it produces is committed back to the repo so the live site auto-redeploys with fresh data.

  1. Refresh 2026 Statcast data via pybaseball — pulls every new pitch incrementally, then rebuilds the per-game feature tables in data/.
  2. Enrich feature tables — adds opposing-starter context, lineup features, and true-talent (empirical-Bayes shrunk) + log5 matchup signals so projections are conditioned on who's actually facing whom.
  3. Backfill missing game-pick rows — re-runs the game model on any completed date the picks log hasn't recorded yet.
  4. Run today's game model — projects win probability for every scheduled game, computes EV against current DraftKings/FanDuel lines, flags positive-EV picks.
  5. Re-grade the season pick log — pulls finals from the MLB Stats API and updates the correct column on every prior pick.
  6. Backfill + run NRFI predictions — runs the No-Run-First-Inning classifier on every scheduled game and fills any past date that doesn't have a NRFI entry yet. Idempotent.
  7. Grade NRFI picks — fetches first-inning linescores from the MLB Stats API and writes 2026_nrfi_accuracy.csv.
  8. Backfill missing past-date player snapshots — for any past date without a snapshot on disk, fetches the actual lineup from MLB box scores and runs the player projection models against it, using only feature rows with game_date < target_date. Idempotent.
  9. Generate today's hitter and pitcher projections — writes both the live hitterspitchers_today.csv the front-end reads and a dated snapshot for tonight's grading.
  10. Grade player snapshots — joins every snapshot to its game's actual box score and rebuilds 2026_player_accuracy.csv, which feeds the accuracy tab and the empirical blend-weight tuner.

Model retraining is a separate, opt-in step — the daily tick uses whatever .pkl files are on disk. When the trainer runs (hitterspitchers_train.py and train_game_model.py), the new game model is written as a candidate first and only promoted to production if it beats the current model on the holdout — the existing model is backed up with a timestamp before the swap. This prevents a bad training run from silently degrading the live site.

Where the data comes from

Every projection is built from live 2026 Statcast pitch-level data. The data pipeline:

  • Pulls fresh Statcast pitches via pybaseball.statcast() incrementally — only new dates get fetched, and the cache (pitch_data_2026.csv) is updated in place.
  • Aggregates each pitch into per-batter and per-pitcher game rows: PA, H, HR (and doubles/triples for Total Bases), BB, K, plus Statcast batted-ball metrics like average exit velocity, max EV, average launch angle, barrel and hard-hit proxies.
  • Computes rolling features for every player at six window sizes — last 5, 7, 10, 14, 21, and 30 games — plus season-to-date and standard-deviation columns. These are the windows the trained models expect at inference time.
  • Computes vs-handedness splits separately so a hitter's "h_rate vs LHP" and "vs RHP" are tracked as distinct features — same for pitchers vs LHB / RHB.
  • Builds opposing-team and opposing-starter context columns so a hitter's projection is conditioned on who they're actually facing, plus true-talent (empirical-Bayes shrunk) rates and log5 matchup features that combine pitcher and lineup true-talent into a single odds-ratio signal.
  • Pulls live odds from The Odds API (DraftKings + FanDuel) and probable starters from MLB Stats API just before each tick.

The output is four tables in data/ — hitter_game_data.csv, pitcher_game_data.csv, team_batting_hand_context.csv, team_pitching_hand_context.csv — that every model reads on every run. Both the trainer and the grader filter all feature rows to game_date < target_date, so no model ever sees information that wasn't available before the game started.

Game predictions

The model that produces today's picks is a gradient-boosted classifier (XGBoost) trained on multiple completed MLB seasons of labeled history. For each 2026 matchup it scores live features built from the day's freshly-refreshed Statcast tables:

  • Both teams' last-10-game offensive stats (OPS, K-rate, BB-rate, runs scored, runs allowed)
  • Each starting pitcher's last-10-game and season FIP, K-BB%, and HR/9
  • Both bullpens' season + last-14-day ERA proxy, WHIP, and K-BB%
  • Season-long team OPS, team K-rate, run differential, and win percentage
  • A home-field flag

The model returns a probability that the home team wins — for example, 57.3%. Whichever team has the higher probability becomes the model pick. The probabilities you see in win-prob bars and pick percentages come straight from this output.

Expected value (EV)

Win probability alone doesn't tell you whether a bet is worthwhile — the odds have to support it. EV is the math that connects the two: 

EV = win_prob × (decimal_odds − 1) − (1 − win_prob)

In plain English: if the model thinks BOS wins 57% of the time and the moneyline is +110 (1.91 in decimal), the bet pays out 91¢ per $1 staked when it wins and loses $1 when it loses. Multiply each outcome by its probability and net them. Anything > 0 is positive EV — the model thinks the line is mispriced in your favor.

A pick is flagged Good Value when EV is at least +2% (a 0.02 floor in my config). All others are Pass. Both DraftKings and FanDuel lines are pulled and the better of the two is used for each side — the same edge you'd get by line-shopping yourself.

NRFI predictions

The NRFI (No Run First Inning) model predicts whether neither team will score in the opening inning — a popular betting market. It's a binary classifier that outputs P(NRFI) for each game, trained on every 2026 game in the Statcast database with a labeled first-inning outcome.

Feature priority is intentional. Full-game pitcher stats are the strongest signal because they're built from 80–120 batters per start — far more stable than first-inning-specific rates (which come from 3 batters). The model uses four feature tiers:

  • Full-game pitcher stats (primary) — each starter's rolling K%, BB%, H%, and HR% over the last 5 and 10 games, plus season-to-date standard deviation and days of rest.
  • Full-game team offense (secondary) — rolling team K%, OBP, and runs per game over the last 5 and 10 games for both lineups.
  • First-inning pitcher rates (tertiary) — per-PA K, BB, and runs-allowed rates in the 1st inning specifically — noisy but inning-specific.
  • First-inning team batting (tertiary) — on-base rate, K rate, and runs scored in the 1st inning.

Four model types are trained each run (L1 logistic regression, gradient boosting, random forest, XGBoost) and the one with the best hold-out AUC is selected. Logistic regression with heavy L1 regularization is the default baseline — it auto-selects the most reliable features and is least prone to overfitting the many correlated rolling windows. A confidence threshold is tuned on the hold-out set before publishing predictions.

The lean shown on the NRFI tab is YES (expect a scoreless first) or NO (expect at least one run). Historical accuracy is tracked in 2026_nrfi_accuracy.csv and graded after every game via the MLB Stats API first-inning linescore endpoint.

Player projections

Pitcher and hitter projections come from two independent model families per stat — a direct counting-stat model and a per-opportunity rate model — that get ensembled at scoring time. For each target the trainer tries random forest, XGBoost, and a small neural net, and keeps the one with the best chronological-holdout MAE. For non-negative integer count targets (H, HR, BB, K, PA, IP, TB) XGBoost uses objective="count:poisson" — the natural loss for count data, which materially helps sparse stats like HR and TB where most rows are zero.

Every model is fit with strong regularization (typical XGB: max_depth=3, min_child_weight=30, reg_alpha=1.0, reg_lambda=3.0) on a chronological train/test split, with a hyperparameter randomized search inside an inner future-fold to prevent leakage. A post-hoc calibration step (isotonic when it beats linear by > 0.002 MAE on the holdout, otherwise linear, otherwise identity) is baked into the saved pickle, so inference always returns calibrated predictions without an extra step.

Pitchers

Five direct count models, plus their per-9 rate counterparts:

  • pitcher_IP.pkl — projected innings pitched
  • pitcher_K.pkl, pitcher_BB.pkl, pitcher_H.pkl, pitcher_HR.pkl — direct counting stats
  • pitcher_K_per_9.pkl, pitcher_BB_per_9.pkl, pitcher_H_per_9.pkl, pitcher_HR_per_9.pkl — per-9-innings rate models

At inference, the final pitcher projection for each stat is (1 − α) × direct + α × (rate × proj_IP / 9). The per-stat weight α is empirically tuned by tune_blend.py against graded historical projections — the rate side leverages the already-well-calibrated IP prediction, the direct side captures volume-rate interactions the rate model can't. Park factors, hand splits, velocity, spin, and pitch-mix percentages all feed in as features.

Hitters

Six direct count models, plus their per-PA rate counterparts:

  • hitter_PA.pkl — projected plate appearances (lineup spot, expected game length, opposing-starter durability)
  • hitter_H.pkl, hitter_HR.pkl, hitter_BB.pkl, hitter_K.pkl, hitter_TB.pkl — direct counting stats (hits, home runs, walks, strikeouts, total bases)
  • hitter_h_per_pa.pkl, hitter_hr_per_pa.pkl, hitter_bb_per_pa.pkl, hitter_k_per_pa.pkl, hitter_TB_per_PA.pkl — per-PA rate models

Same ensemble math as the pitcher side: (1 − α) × direct + α × (rate × proj_PA), with α tuned per stat from graded outcomes. Each hitter is conditioned on the opposing starter (true-talent K%, H%, HR% against same-handed batters, plus the log5 matchup signal) so the same hitter shows different numbers depending on who's pitching. FanDuel player prop lines are pulled alongside the projection for direct comparison.

Pitcher and hitter projections are estimated independently and may not sum perfectly across a matchup. Each is a standalone estimate — best used to compare players against each other, not to add up.

How picks are graded

Once a game is final, I pull the box score from the MLB Stats API and compare the model's pick to the actual winner:

  • actual_winner = the team that scored more runs
  • correct = 1 if the model's pick matches the actual winner, 0 if it doesn't, blank if the game hasn't finished yet

Picks flagged Good Value at publish time get assigned a 1-unit bet for accounting. Profit and loss are calculated against the moneyline that was published when the pick was made — not the closing line:

  • Win on +120 → +1.20 units
  • Win on -150 → +0.67 units
  • Loss → -1.00 unit
  • Pass (not bet) → 0.00 units

Running ROI is cumulative profit divided by total units wagered. The Season Accuracy tab shows the cumulative pick accuracy across all graded games — including the ones flagged Pass — so the chart reflects the model's overall predictive performance, not just bet outcomes.

Player projection accuracy

Game-pick accuracy is binary — the predicted winner either won or didn't. Player projections are continuous, so they're scored differently. Every day's hitter and pitcher projections are saved as a dated snapshot in outputs/hitterspitchers_<date>.csv; once the game completes, those projections are joined to the actual MLB box score (pulled from the MLB Stats API) and I record the per-stat difference in 2026_player_accuracy.csv.

For dates earlier in the season that don't yet have a snapshot on disk (typical for the first cron run after deploying), the pipeline backfills them by pulling the actual lineup that played from the box score and running the projection model with target_date set to that game's date. The model only ever sees rows where game_date < target_date, so backfilled projections use the same information the model would have had if it had been run live on that day — no future-data leakage.

Because the data refresh, projection, and grading all happen inside the same cron tick, the projections being graded each day are produced from the same 2026 Statcast features that today's projections use. The grader is fully idempotent: re-running it pulls fresh box scores for any game that's now complete and overwrites the log.

Bias calibration

Calibration is done inside training, not as a separate post-hoc shift after the fact. When each model is fit, the trainer holds out the most recent 15% of the training window, predicts on it, and fits a mapping from raw predictions to actual outcomes — isotonic (monotone, non-parametric) when it beats a linear a + b · ŷ fit by more than 0.002 MAE on the holdout, otherwise linear, otherwise the identity. The chosen calibration is baked into the saved .pkl so inference is one step.

Why isotonic matters: linear calibration can only shift and scale. Isotonic can fix curved bias — the typical "model under-predicts the top quintile of HR and over-predicts the bottom quintile" pattern — that no single (a, b) pair can correct. The safety margin guarantees a model can never get worse from calibration: if isotonic doesn't beat linear, linear is used; if linear doesn't beat raw, the identity is used.

The blend weights themselves are also tuned empirically. tune_blend.py grid-searches α for each stat against graded outcomes and prints a recommended config; pasting it into hitterspitchers_today.py propagates new weights into every snapshot via backfill_blend_components.py — no full retrain required, since the components on the snapshot are already saved.

The Season Accuracy tab's Player Predictions sub-tab summarizes those graded projections in three ways:

  • MAE (mean absolute error) — the average distance from a projection to the actual outcome. Lower is better. For pitcher strikeouts, an MAE of 1.4 means the typical projection lands within ~1.4 K of the real number.
  • Bias — the average signed error (proj − actual). A positive bias means the model over-projects; a negative bias means it under-projects.
  • Within ±tolerance — the share of projections that landed inside a stat-specific tolerance band (e.g. ±1.5 K for pitchers, ±0.5 HR for hitters). This is the most intuitive number for non-stats readers.

Because player projections are graded fresh against MLB Stats API box scores after every slate, the player accuracy view fills in over time as more games are played.

What this site is, and isn't

This is research and analytics, not advice. The model is right around 60% of the time on graded picks — meaningfully better than 50/50, but no projection model wins every day, every series, or every season. Edges in baseball are small and noisy, and the models here are no exception.

Use these picks as one input among several. Cross-check against your own knowledge of the matchup, weather, late-breaking lineup news, and bullpen availability. Bet only what you can afford to lose.

How are picks generated?
Each day a pipeline (daily_update.py) pulls fresh stats from the MLB Stats API and Statcast, runs gradient-boosted models for moneyline win probability and pitcher/hitter stat projections, calibrates the outputs against recent graded results, and writes the projections to the live site. See Methodology for the full chain.
When are picks posted?
The predictions are generated at 7 AM, 12 PM, and 7 PM ET. The website updates visuals and accuracy after all of these for self educated picks.
What sportsbooks are referenced?
All EV is built from Fanduel lines.
Can picks lose?
Yes. The model outputs probabilities, not certainties. The Performance tab shows the actual hit rate over the season — including the losing stretches. A 53% moneyline model is still wrong 47% of the time.
Is there a guarantee?
No. Anyone telling you they have a guaranteed sports-betting system is selling something dangerous. This is a research and analytics tool. Use it to inform decisions, not as a promise of returns.
How is performance graded?
Every projection the model emits is snapshotted before first pitch. After games finish, actuals are pulled from official MLB box scores and compared. Moneyline picks are scored by win/loss; player projections by mean absolute error and "within tolerance" rate. The grading code is the same code that powers the Performance tab — nothing is curated after the fact.
